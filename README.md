# O2O 红包核销系统（通用版）

一套可以整套交给别人使用的 O2O 红包核销工具：**导入底表 → 自动核对 → 出报告 → 看板查数**。
换一批门店、型号、月份，只用换自己的 Excel 底表，代码不用改。

> **不想敲命令？** 根目录直接双击 `①建我自己的库.bat` → `②导入我的表格并核对.bat` → `③打开我的看板.bat`。数据库会自动建在 `data/persons/你的名字/redpacket.db`。完整操作见《O2O 红包核销操作手册（总册）》，四张 Excel 模板也作为附件放在该手册末尾。

---

## 1. 它能做什么

| 能力 | 说明 |
| --- | --- |
| 底表模板 | 四张表各一份独立模板（`templates/`），带「填写说明」页，照着填就不会被退回 |
| 底表导入 | 一个 Excel 里放多张工作表，按表名自动识别「下单 / 发放 / 政策 / 期初」四类数据 |
| 一人一库 | 每人建自己的 SQLite 库，数据只落本机，不存在「都往一个库里传」 |
| 四项核对 | ① 政策核销（单台金额 vs 政策标准）② 下单红包核销（发放 vs 下单）③ 零售红包核销（累计零售 vs 累计下单）④ 数据检查（缺政策、缺下单、缺期初） |
| 留痕 | 每次导入一批（批次号）、每次核对一批（批次号），同口径重复跑覆盖旧结果，不堆重复批次 |
| 报告 | 生成多工作表 Excel：核对总览 / 差异汇总 / 三项核对明细 / 数据检查 / 政策缺口 / 导入日志 / 口径说明 |
| 看板 | 本地网页：概览、数据导入、数据明细、核销结果、核对口径，支持筛选、分页、导出、拖拽上传、一键重跑 |

## 2. 环境准备（一次性）

```bash
# Python 3.10+ 即可，无数据库服务依赖（SQLite 单文件）
pip install -r requirements.txt
```

Windows 上把 `python3` 换成 `python`，`.sh` 脚本对应改成双击 `.bat` 或直接在命令行执行同样命令。

---

## 3. 先建自己的库（一人一套，不共用）

```bash
python scripts/init_person.py --name 张三
# → 建库 data/persons/张三/redpacket.db，并生成使用说明
```

之后所有命令指向自己的库，两种写法等价：

```bash
# 写法一：命令行带 --db
python scripts/import_data.py --db data/persons/张三/redpacket.db
python scripts/run_audit.py   --db data/persons/张三/redpacket.db
python scripts/serve_dashboard.py --db data/persons/张三/redpacket.db --port 8899

# 写法二：先设环境变量，后面的命令都不用再带（Windows PowerShell 用 $env:REDPACKET_DB="..."）
export REDPACKET_DB=data/persons/张三/redpacket.db
```

别人的库在别人自己的机器/目录里，**不要把别人的底表导进你的库**：混在一个库里，批次号、期初累计、重复导入覆盖都会互相干扰。

---

## 3.5 三步跑通（在自己的库里）

```bash
# 第 1 步：建库（--reset 会清空重来，第一次可不加）
python3 scripts/init_db.py

# 第 2 步：把底表放进 data/inbox/，然后导入
cp 你的底表.xlsx data/inbox/
python3 scripts/import_data.py

# 第 3 步：核对并出报告
python3 scripts/run_audit.py
```

报告在 `data/out/`：`红包核对报告_<批次>_<时间>.xlsx`，同时更新一份 `最新核对报告.xlsx`。

一键跑完（导入 + 核对）：

```bash
bash 一键跑全流程.sh
```

打开看板：

```bash
python3 scripts/serve_dashboard.py --port 8899
# 浏览器访问 http://127.0.0.1:8899/
```

## 4. 用自己的数据：底表怎么准备

### 4.1 用模板（`templates/` 里四张表各一份）

| 模板文件 | 对应工作表 | 用途 |
| --- | --- | --- |
| `1_下单明细_模板.xlsx` | 下单明细 | 与现有系统导出同列：月份、订单日期、渠道、门店名称、型号、品类、数量、金额、类型、大区战区 |
| `2_红包发放_模板.xlsx` | 红包发放台账 | 同列：月份、渠道、门店名称、型号、品类、红包类型、本次发放数量、单台发放金额、本次发放金额 |
| `3_红包政策_模板.xlsx` | 红包政策 | 每月每型号的下单、零售单台标准 |
| `4_期初累计_模板.xlsx` | 期初累计 | 基准月为止的累计下单、累计零售 |

每个模板都带一张「填写说明」页，写明该字段是否必填、怎么填、示例长什么样。四份表可以分别填、分别上传，也可以合成一个 Excel 一次导入（表名保留关键词即可）。
`samples/样例底表_2026H1.xlsx` 是四表合一的示例，含三类刻意构造的异常，可用来验证系统是否跑通。

### 4.2 四张表的必需列

| 工作表（表名含关键词即可） | 关键词 | 必需列 | 可选列 |
| --- | --- | --- | --- |
| 下单明细 | 下单 / 订单 / 销售 | 门店名称、型号、月份、数量 | 渠道、门店编码、下单金额 |
| 红包发放 | 发放 / 台账 / 红包 | 门店名称、型号、月份、数量、单台金额 | 红包类型、渠道、门店编码、红包金额、累计数量 |
| 红包政策 | 政策 / 标准 | 型号、生效起始月、下单标准、零售标准 | 渠道、政策文号 |
| 期初累计 | 期初 / 累计 | 基准月、门店名称、型号、累计下单数量 | 渠道、门店编码、前期零售红包数量、累计下单红包数量 |

列名不必一字不差：`门店/客户名称`、`机型/产品型号`、`月份/年月/账期`、`单台红包/红包标准` 这类常见写法都能认。
表名不用完全对上，含关键词即可，例如「1月红包发放台账」「2026年O2O红包政策」都能识别。

### 4.3 三个容易被退回来重传的坑

1. **月份列要能识别**：`2026-01`、`2026年1月`、`202601`、Excel 日期格式都行；只写 `1` 也能识别，但政策表要配「生效起始月」列，否则只能靠文件名带「1月」。
2. **数量要填净数量**：退货用负数，不要用「退货数量」单列，否则累计会算错。
3. **政策表每月一份快照**：一行一个型号 + 一个月，不要用「从某月起长期有效」的写法（系统按月判定，跨月无政策会直接判异常并列出缺口月份）。

## 5. 看板怎么用

**网页端上传（推荐给非技术同事）**

1. 用 `--db` 指向自己的库起看板，打开 `http://127.0.0.1:8899/`，左侧底部会显示当前是哪个库；
2. 进「数据导入」，把 Excel 拖进去，只写入这台机器上你自己的库，自动识别四类表，页面回显每张表写入/失败行数；
3. 回「概览」点「重跑核对」，结果与报告同时更新。

**接口调用（便于接自动化）**

```bash
curl -X POST "http://127.0.0.1:8899/api/import?name=1月红包.xlsx" --data-binary @1月红包.xlsx
curl -X POST "http://127.0.0.1:8899/api/recheck"
```

**让别人也能访问**（同一局域网内多人用）：

```bash
python3 scripts/serve_dashboard.py --host 0.0.0.0 --port 8899
# 同事访问 http://你的IP:8899/
```

## 7. 判定口径（可改）

| 参数（config/settings.json） | 默认 | 含义 |
| --- | --- | --- |
| `baseline_period` | 2025-12 | 期初累计的截止月，累计从这里开始累加 |
| `judge_from_period` | 2026-01 | 从这个月起做判定，之前月份只入库不判定 |
| `amount_tolerance` | 0.5 | 单台金额允许的误差（元），超出才判异常 |
| `qty_tolerance` | 0.0001 | 数量允许的误差（台） |

判定规则：

- **政策核销**：实发单台 > 当月政策标准 + 容忍度 → 异常；低于标准不标记；找不到当月政策 → 异常并注明缺口月份。
- **下单红包核销**：门店当月下单红包发放数量 > 当月净下单数量 → 异常。
- **零售红包核销**：期初累计零售 + 其后各月累计零售发放 > 累计下单 → 异常；缺期初给预警（按 0 起算，需补数后复核）。
- **数据检查**：政策缺口、某月缺下单数据、型号从未下单、缺期初 → 只预警不判违规。

口径改了不需要动代码，改完 `settings.json` 直接重跑核对，同源数据会覆盖上一批结果。

## 7.5 多人怎么用：各管各的库

| 做法 | 结果 |
| --- | --- |
| 每人 `init_person.py --name 自己` 建库，各自导入自己的底表（推荐） | 互不影响，谁的异常谁负责；报告、批次号都在自己库里 |
| 大家一起往一个库里传 | 不推荐：期初累计会串、重复导入互相覆盖、批次号对不上责任人 |

需要汇总时，各自跑完核对后只交换**报告**（`data/out/红包核对报告_*.xlsx`），不交换数据库文件。

## 8. 交给别人的方式

1. 把整个目录（去掉 `data/redpacket.db`、`data/inbox`、`data/archive` 里的真实业务文件）打包发给对方；
2. 对方 `pip install -r requirements.txt` → 放自己的底表 → `bash 一键跑全流程.sh`；
3. 需要多人看数时用 `--host 0.0.0.0` 起看板。

真实业务数据和政策原文不要提交到 Git 仓库，`.gitignore` 已覆盖 `data/`、`*.db*`（含 WAL）、`*.xlsx`、`config/my_db.txt`、`.env` 等（`samples/`、`templates/` 白名单除外），详见第 12 节。

## 9. 命令与参数速查

所有脚本都可以直接 `python3 scripts/xxx.py --help` 查看参数。

| 脚本 | 作用 | 常用参数 |
| --- | --- | --- |
| `init_person.py` | 给一个人建独立库（默认 `data/persons/<姓名>/redpacket.db`） | `--name 张三`（必填）、`--dir`、`--reset` |
| `init_db.py` | 建库建表，不改数据 | `--db <库路径>`、`--reset`（删库重建，慎用） |
| `import_data.py` | 导入 `data/inbox/` 下的 Excel，导入后自动归档 | `--db`、`--dir <待导入目录>` |
| `run_audit.py` | 跑四项核对并出 Excel 报告 | `--db`、`--no-report`（只核对不写文件） |
| `serve_dashboard.py` | 起本地看板 | `--db`、`--port 8899`、`--host 0.0.0.0` |
| `make_templates.py` | 重新生成 `templates/` 四张模板 | 无 |
| `generate_sample_data.py` | 重新生成 `samples/` 样例底表 | 无 |

环境变量（详见 `.env.example`）：`REDPACKET_DB`（库路径）、`PORT`、`HOST`、`PYTHON`。
优先级：**命令行 `--db` > 环境变量 `REDPACKET_DB` > 默认 `data/redpacket.db`**。

## 10. 报告里有什么

每次核对生成 9 个工作表的 Excel（`data/out/`，同时覆盖一份 `最新核对报告.xlsx`）：

| 工作表 | 内容 |
| --- | --- |
| 核对总览 | 批次号、核对月份范围、期初基准月，四项核对的项数 / 合规 / 异常 / 预警 / 差异合计，以及四类台账的数据条数 |
| 核对1 政策核销 | 每个「门店×型号×月份」实发单台金额 vs 当月政策标准 |
| 核对2 下单红包 | 门店当月发放数量 vs 当月净下单数量 |
| 核对3 零售累计 | 期初累计零售 + 各月累计零售发放 vs 累计下单 |
| 数据检查 | 政策缺口、某月缺下单数据、型号从未下单、缺期初（只预警不判违规） |
| 差异汇总 | 按「核对项 × 月份 × 渠道」汇总项数、异常数、差异合计 |
| 政策缺口 | 哪些月份哪些型号缺政策，附处理建议 |
| 导入日志 | 每个批次、文件、工作表的写入行 / 失败行 / 错误信息 |
| 核对口径说明 | 本次核对使用的参数与判定规则原文，便于复核和解释 |

状态含义：`PASS` 通过、`FAIL` 异常（需处理）、`WARN` 预警（数据不全，不判违规）。

## 11. 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 提示「还没建库，请先建库」 | 先跑 `init_person.py --name 你的名字`，或双击 `①建我自己的库.bat` |
| 导入后行数为 0 | 表名里没有关键词（下单/发放/政策/期初），或必需列缺了，看报告的「导入日志」页错误列 |
| 某月大量「缺政策」 | 政策表按「每月一份快照」填，不要用「长期有效」；或检查型号写法是否与下单表一致 |
| 金额判异常但算着是对的 | 看 `amount_tolerance`（默认 0.5 元），四舍五入造成的分差在容忍度内就不报 |
| 数量累计对不上 | 退货要填负数进数量列，不要单开「退货数量」列 |
| 看板打不开 / 端口被占 | 换端口：`serve_dashboard.py --port 8900`；或先关掉旧进程 |
| 打开报告提示文件损坏 | 核对时报告文件被 Excel 占用，关掉 Excel 重跑 |
| `pip` 装不上 openpyxl | 换镜像：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple -r requirements.txt` |
| Windows 双击 `.bat` 窗口一闪而过 | 在命令行里手动执行同名命令，能看到完整报错 |
| 中文乱码 | `.bat` 已设 `chcp 65001`；Excel 请存为 `.xlsx`，不要用旧版 `.xls` |

## 12. 数据安全与合规

**可以上传到 Git 的**：代码、`db/schema.sql`、`config/settings.json`（只有口径参数）、`web/` 前端、`templates/` 空模板、`samples/` 伪造样例、`.env.example`。

**绝对不能上传的**：

- 真实底表与报告：`data/` 下全部内容（`inbox/`、`archive/`、`out/` 报告、`persons/` 个人库）
- SQLite 文件：`*.db`、`*.db-wal`、`*.db-shm`（WAL 文件里同样有数据）
- 个人机器路径：`config/my_db.txt`（每人不同）
- 小票、转账截图等图片
- 任何 Token、密钥、`.env`

`.gitignore` 已把上述类型全部拦截，并且白名单收窄到 `samples/样例*.xlsx`、`samples/底表模板*.xlsx`、`templates/*_模板.xlsx`——真实业务表即使误丢进这两个目录也会被挡。

**仓库里的样例与模板均为虚构示例**：门店名（示例门店A/B/C）、型号（65X1A / 75X1A / 85X2B / 98X2B）、政策文号（`DEMO-2026-01-65X1A`）、红包金额全部是编造的，与任何真实品牌、门店、政策标准无关，可直接用于公开演示。

**团队协作口径**：一人一库，只交换报告（`data/out/红包核对报告_*.xlsx`），不交换数据库文件；需要看数就让对方用 `--host 0.0.0.0` 起看板，不要把库发出去。

**如果不小心已经提交过真实数据**：

```bash
git rm --cached -r .        # 先取消跟踪（文件保留在本地）
git add .                   # 按新的 .gitignore 重新暂存
git commit -m "chore: 移除误提交的业务数据"
```
若已 push 过，仅这样删除不够（历史里还在），建议**换一个新仓库重新提交**，或重写历史（`git filter-repo`）。

## 13. 环境与版本

- Python 3.10+，第三方依赖只有 `openpyxl`（其余为标准库）
- 数据库：SQLite 单文件，无服务端，无需安装
- 看板：Python 内置 `http.server`，浏览器打开即可，无需 Node
- 跨平台：Windows（`.bat`）、macOS（`.command`）、Linux/macOS 命令行（`.sh`）
- 许可证：内部使用，未对外授权；如需公开请先确认数据与政策文本的合规性
